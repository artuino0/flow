# Changelog

### [0.54.0] - 2026-09-02
#### [add]
- ERD-84 (Gestión de usuarios: invitar, listar y administrar accesos - `Screen/Usuarios`) - cierra el gap documentado desde la 0.51.0: hasta esta HU no existía ningún endpoint bajo `/api/users` ni forma de crear un usuario desde la UI (solo `scripts/seed*.mjs`). Creado y trabajado a pedido directo del usuario ("créalo y trabájalo").
- Decisión del usuario, vía `AskUserQuestion` (invitación por enlace manual vs. SMTP real vs. otro): **SMTP real ahora** - la plataforma no tenía ninguna capacidad de envío de correo (ERD-50 seguía en el backlog); esta entrega construye una utilidad SMTP mínima en vez de un enlace que el admin copia/pega a mano.
- **Invitación por correo real**: `users` ganó `invitation_token_hash`/`invitation_expires_at` (migración `0024_erd84_user_invitations`, sin RLS propia - columnas nuevas sobre una tabla que ya la tenía). Un usuario invitado se crea con `isActive=false` (gate real que bloquea el login hasta aceptar) y un `password_hash` placeholder inutilizable (hash de un valor aleatorio que nunca se entrega a nadie - la columna es `NOT NULL`, no hay forma de dejarla vacía). Se guarda el HASH (sha256) del token de invitación, nunca el crudo - mismo criterio que `password_hash`.
- El token de invitación codifica el `tenantId` como prefijo (`<tenantId>.<secreto-aleatorio>`) a propósito: `acceptInvitation()` (público, sin sesión) necesita resolver el tenant del usuario invitado ANTES de poder consultarlo, y la única conexión de runtime (`erp_app`) tiene RLS real - una consulta `SELECT ... WHERE invitation_token_hash = ...` sin `withTenant()` habría devuelto siempre 0 filas (RLS filtra por `current_setting('app.tenant_id')`, que sin `withTenant()` queda sin setear). Conocer el tenantId no ayuda a adivinar el secreto de 32 bytes aleatorios. Enlace de expiración de 7 días (copy exacto del correo real, ver abajo).
- `server/utils/mailer.ts` (nuevo, via `nodemailer`): `sendInvitationEmail()`, configurado 100% por variables de entorno (`SMTP_HOST/PORT/USER/PASSWORD/FROM`, `APP_BASE_URL` para armar el enlace) - sin fallback silencioso: si falta configurar SMTP, invitar un usuario falla con 500 y un mensaje explicando qué completar en `.env`. Revisado con las herramientas de Pencil, a pedido explícito del usuario ("Email/Invitación Usuario en pen") DURANTE la construcción de esta HU - el `.pen` tiene un segundo nodo (`Email/Invitación Usuario`, separado de `Screen/Usuarios`) con el diseño real del correo, copy exacto y la ruta real del enlace de aceptación (`app.erpdinamico.com/invitacion/<token>` - fija la convención `/invitacion/:token`, no `/aceptar-invitacion?token=`, corregida en el plan original tras revisarlo).
- `server/utils/users.ts` (nuevo, mismo patrón que `rolePermissions.ts`/`moduleEntities.ts`): `listUsers`, `inviteUser` (valida el rol contra el tenant, `DuplicateEmailError` en correo repetido), `resendInvitation` (token nuevo, invalida el anterior), `updateUser` (rol/estado activo - no permite editar la propia cuenta, `CannotEditSelfError`, para que un admin no se bloquee a sí mismo), `cancelInvitation` (borra una invitación todavía pendiente - no sirve sobre una cuenta ya activa) y `acceptInvitation` (público). Endpoints: `GET/POST /api/users`, `PUT/DELETE /api/users/:id`, `POST /api/users/:id/resend-invitation`, `POST /api/users/accept-invitation` (público, agregado a `PUBLIC_PATHS`).
- `pages/usuarios.vue` (nuevo, `Screen/Usuarios` del `.pen`, revisado con las herramientas de Pencil - `[[pencil-antes-de-frontend]]`) + `pages/invitacion/[token].vue` (nuevo, sin mock propio en el `.pen` - reusa fielmente el layout partido de `pages/login.vue`) + link "Usuarios" en `AppNav.vue` (gateado a administrador, mismo guard que Módulos/Roles). Columnas Usuario/Rol/Estado/Acciones y el modal "Invitar usuario" (Correo electrónico + Rol, botón "Enviar invitación") copiados 1:1 del diseño, incluido el detalle de que el estado se muestra como un punto de color + texto (no una badge con fondo, a diferencia de Activo/Inactivo en Módulos). Interpretaciones documentadas en el código donde el mock no alcanza (solo dibuja 3 filas "Activo" + 1 "Invitación pendiente" con lápiz+basurero, sin mostrar edición ni una invitación vencida): lápiz abre "Editar usuario" (rol + acceso activo/inactivo); basurero cancela la invitación si está pendiente o desactiva el acceso si ya es una cuenta activa; enlace "Reenviar" agregado junto al estado pendiente (necesario porque el token vence a los 7 días).
- Validado: `npx nuxt typecheck` limpio; suite de unit/integración **197/197** (incluye `test/integration/users.test.ts`, nuevo, 20 casos contra Postgres real con `nodemailer` mockeado - invitar, rol/correo duplicado o de otro tenant, aceptar con el token real del correo, token inválido/reutilizado/expirado, reenviar invalida el token anterior, editar rol/estado, no poder editarse/cancelarse a sí mismo, cancelar una invitación pendiente - y `test/unit/mailer.test.ts`, nuevo, 3 casos sobre el HTML del correo incluido el escapado de HTML en campos con entrada de usuario). `npx nuxt build` compiló cliente y servidor SSR sin errores (181 módulos SSR OK), pero el empaquetado de Nitro no completó dentro del límite del sandbox (misma limitación de todas las entregas de esta sesión) - se recomienda correr `npm run build` localmente antes de desplegar.
- Pendiente para el usuario: `npm run db:migrate` local para aplicar la migración `0024`; completar `SMTP_HOST/PORT/USER/PASSWORD/FROM` y `APP_BASE_URL` en `.env` (ver `.env.example`) antes de invitar usuarios en un ambiente real - sin esas variables, `POST /api/users` falla con 500 explicando qué falta.

### [0.53.0] - 2026-09-02
#### [add]
- ERD-83 parte 2 (2FA por TOTP + sesión deslizante con aviso de inactividad) - cierra la HU de seguridad de acceso, cuya parte 1 (rate limiting + política de contraseñas) se entregó en la 0.51.0.
- **2FA por TOTP**: `server/utils/totp.ts` (nuevo, via `otplib` v13 + `qrcode`) - genera secreto, URI `otpauth://` y QR como data: URL; verifica códigos de 6 dígitos con tolerancia de ±30s de desfasaje de reloj. Columnas nuevas `users.totp_secret`/`users.totp_enabled` (migración `0023_erd83_totp`, sin RLS propia - son columnas nuevas sobre una tabla que ya la tenía). `totpEnabled` solo pasa a `true` tras confirmar un código real de la app autenticadora (`POST /api/auth/totp/verify`) - un `POST /api/auth/totp/setup` a medias, nunca confirmado, no dejar la cuenta en un estado raro. `POST /api/auth/totp/disable` re-exige la contraseña actual, mismo criterio que el cambio de contraseña de la parte 1.
- **Login en dos pasos**: `POST /api/auth/login` ahora devuelve `{requiresTotp: true, tempToken}` en vez de abrir sesión cuando el usuario tiene 2FA activo - el tempToken (JWT de 5 min, nunca en cookie) se manda junto con el código a `POST /api/auth/login/totp` (nuevo), que recién ahí abre la sesión real. Un código TOTP incorrecto se limita con el mismo mecanismo de rate limiting de la parte 1, pero en un bucket propio (no comparte contador con intentos de contraseña de la misma cuenta).
- **Refresh token + sesión deslizante** (pedido explícito del usuario durante esta HU, no estaba en el alcance original de ERD-83): el access token bajó de 8h a 15 min; una nueva cookie httpOnly separada (`erp_refresh_token`, 7 días) permite renovarlo sin re-loguear vía `POST /api/auth/refresh` (nuevo). `server/utils/auth.ts` ganó `issueSessionCookies()` (emite ambas cookies, usado por los tres puntos donde arranca o se renueva una sesión) y los tipos de token `totp-pending`/`refresh`, cada uno con su propio `purpose` para que nunca puedan colarse como sesión válida el uno del otro (verificado explícitamente en `server/middleware/auth.ts` y con tests). Limitación conocida y documentada en el código: al ser JWTs sin tabla de sesiones, no hay forma de revocar un refresh token individual antes de su vencimiento natural (ej. "cerrar sesión en todos los dispositivos") sin rotar el `JWT_SECRET` global.
- **Modal de inactividad** (mismo pedido, sin mock en el `.pen`): `composables/useIdleTimeout.ts` + `components/InactivityWarningModal.vue`, montado desde `layouts/default.vue`. Con actividad real (mouse/teclado/scroll/touch) el access token se renueva solo de fondo (throttleado a lo sumo cada 5 min); a los 60s sin actividad aparece un aviso con cuenta regresiva de 60s - si nadie confirma "Seguir conectado", se cierra la sesión y se redirige a `/login?reason=inactividad` (mensaje informativo ahí). Una vez que el aviso aparece, solo el botón lo confirma - mover el mouse por encima no alcanza, para que un roce accidental del cursor no mantenga viva una sesión realmente abandonada.
- **Pantalla "Mi cuenta"** (`pages/mi-cuenta.vue`, nueva, enlazada desde el avatar del header): cambiar contraseña (usa el endpoint ya existente de la parte 1, que hasta ahora no tenía UI) y activar/desactivar 2FA (QR + carga manual del secreto + confirmación con código). Sin mock en el `.pen` para ninguna de las dos cosas - revisado antes de construir (`[[pencil-antes-de-frontend]]`): el único Screen con "cuenta" en el nombre es "Registro Paso 1 - Tu cuenta" (alta de una organización nueva, no esto), y ningún Screen menciona 2FA/inactividad/sesión. Se construyó siguiendo el lenguaje visual general de la app (mismas cards, inputs e íconos que el resto).
- Corregido en el camino (mismo hallazgo que en ERD-78, esta vez en `server/middleware/auth.ts`): un token `totp-pending` o `refresh`, al estar firmados con el MISMO secreto que un access token real, pasarían `verifyAuthToken` sin problema si no se chequeara explícitamente su `purpose` - sin ese chequeo, alguien con solo un tempToken de 2FA (obtenido apenas con la contraseña, sin haber completado el segundo factor) podría haberlo usado como sesión válida durante su ventana de 5 minutos.
- Validado: `npx nuxt typecheck` limpio; suite de unit/integración **174/174** (incluye `test/unit/auth.test.ts` y `test/unit/totp.test.ts`, nuevos - los tres tipos de token y la lógica de TOTP nunca habían tenido test propio, pese a que todo el login dependía de ellos). No se agregaron tests de integración contra Postgres para los endpoints de login/2FA/refresh en sí (a diferencia del resto de esta sesión) - siguiendo el mismo patrón ya establecido en el proyecto de que `login.post.ts` nunca tuvo test directo propio, solo se ejercita via `test/e2e/` (servidor real). `test/e2e/*` no llegó a correr - depende del build completo, ver abajo. `npx nuxt build` compiló cliente y servidor SSR sin errores (173 módulos SSR OK), pero el empaquetado de Nitro no completó dentro del límite del sandbox (misma limitación de todas las entregas de esta sesión) - se recomienda correr `npm run build` y la suite e2e completa localmente antes de desplegar, dado que esta HU toca el flujo de login de punta a punta.
- Pendiente para el usuario: `npm run db:migrate` local para aplicar la migración `0023`; con esto quedan entregadas las 4 HUs originalmente priorizadas (ERD-77/78/80/83) más esta extensión de ERD-83. El gap de gestión de usuarios (`Screen/Usuarios`, sin backend, documentado en la 0.51.0) sigue sin ticket propio.

Solo valida la FORMA final de cada fila ya armada - la semántica de copia (`copyFrom`: copiar una vez al elegir la relación, nunca recalcular después contra la entidad relacionada actual - snapshot) es responsabilidad del formulario (ERD-71/72), no de este generador.
  - `'select'` → `validationRules.options: [{ value, label, color? }]`, `z.enum([...])` sobre los `value`.
  - `'multiselect'` → mismo formato de `options`, `z.array(z.enum([...]))`.
  - Los tres quedan también registrados en la validación server-side de `entity_fields` (ERD-67): crear un campo `tabla` sin `columns`, o `select`/`multiselect` sin `options`, da 422.
